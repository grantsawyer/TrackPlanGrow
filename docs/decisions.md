usually at the user's request; they stay so a choice isn't reversed by accident. When you change this area, update

- **Rules stamp results on the transaction (2026-11-02).** Alternatives: joining rules in the view (can't express several conditions in
  SQL readably) or applying once only (edits and deletes wouldn't follow, cleaning up a mistaken rule would be manual). All matching
  rules run, first to set a field wins, rather than only the first match, so a tagging rule can sit beside category rules. The category
  condition tests Plaid's category, not an earlier rule's result, so order can't change what matches and rules can't trigger themselves.
- **Rewards spent are transactions (2026-11-04; replaced 2026-11-03's redemptions kept outside spending).** A trip costs the
  same whether cash or points paid, so a points-paid purchase is a manual cost plus a rebate in the same category: the
  category nets to zero (no money moved) and the tag, on the cost only, counts what the trip cost. Rejected: redemptions
  beside spending with a separate "paid with rewards" figure (the user: rewards airfare and cash airfare are one category
  for an event, and budgets should include both); the rebate as income (it would raise income and leave the category's
  spending in); a fixed cents-per-point (value per point is measured from the cash value entered). Card credits stay
  refunds (they offset the expense and so its rewards); a cash sign-up bonus is income; neither is rewards used.
